# iBilim — агент школьной программы

Планирование уроков, персональная домашка и диагностика пробелов, построенные на
государственной типовой учебной программе Казахстана.

**Одна сущность связывает всё — код цели обучения (`7.2.1.4`):**

```
граф целей → КТП (дата→цели) → пакет урока (КСП) → персональная домашка →
проверка (веб / фото / бумага) → карта пробелов → следующий урок
```

## Проблема

- КСП обязателен на каждый урок: до 20 документов в неделю на учителя. Готовые планы в стране
  уже продают за деньги (`plani.kz`) — боль подтверждена рынком.
- Рекомендованные сборники СОР/СОЧ разошлись по интернету, и министерство само признаёт, что
  учитель их для оценивания не использует: свежие варианты пишутся руками.
- Ученик получает балл, а не диагноз. Какая именно цель не усвоена — не видно до СОР.
- Персонализировать 30 тетрадей в день физически невозможно.

## Что делает прототип

| | |
|---|---|
| **Учителю** | КТП на четверть из целей программы; пакет урока (КСП, объяснение, типовые ошибки, задания трёх уровней); выдача персональной домашки классу; сводка «цель 7.2.1.4 не взяли 14 из 28» с рекомендацией |
| **Ученику** | домашка под его пробелы (60% тема урока, 40% добор), сдача с телефона, компьютера или бумажного бланка, разбор ошибок вместо балла |
| **Отдельно** | индекс внешней помощи: метод решения сверяется с тем, что класс реально проходил |

## Детектор «решение из будущего»

Списанная у ИИ домашка ломает не оценку, а диагностику: система запишет цель как освоенную и
перестанет её тренировать. У нас есть множество пройденных целей на конкретную дату конкретного
класса, поэтому сигнал проверяемый: *«решено через подобие треугольников — цель 8.1.2.3,
вторая четверть 8 класса»*.

Стилометрию не используем сознательно: у публичных ИИ-детекторов 61,3% ложных срабатываний на
текстах неносителей языка. Автоматических санкций нет — высокий индекс попадает в очередь
учителя с объяснением оснований.

## Доступность как требование, а не опция

Две из пяти семей в Казахстане не имеют компьютера. Поэтому канал сдачи не влияет ни на
персонализацию, ни на оценку: бумажный бланк, телефон (PWA) и школьный компьютер равноправны,
ученик без устройства получает такую же персональную домашку и такой же разбор — печатным листом.

## Архитектура

```
adilet: программы ─┐
типовые уч. планы ─┼─▶ граф целей ─┬─▶ планировщик КТП ─▶ пакет урока (LLM + кеш)
оглавления книг ───┘   7.2.1.4     ├─▶ генератор заданий ─▶ бланк / веб-форма
                        + deps     ├─▶ проверка: sympy + дескрипторы ─▶ баллы, разбор
фото / веб-ввод ──────────────────▶├─▶ mastery (ученик × цель) ─▶ сводка учителю
                                   └─▶ детектор внешней помощи
```

Стек: Python 3.11 + FastAPI + SQLite, OpenAI Structured Outputs, sympy для арифметики,
Vite + React (PWA). Один сервис отдаёт и API, и статику — одна публичная ссылка.

## Масштабирование

Задания кешируются по ключу `(цель, уровень, язык)`, различаются только параметры варианта
(`seed`), поэтому один сгенерированный шаблон обслуживает тысячи классов, и стоимость на
ученика падает с ростом. Граф целей одинаков для всей страны; новый предмет — это загрузка
ещё одного приложения к приказу, а не переписывание продукта.

## Ограничения прототипа (честно)

- Демо-вертикаль: 7 класс, алгебра, один раздел, интерфейс на русском.
- Авторизации нет: роль передаётся параметром. Это заглушка, не решение.
- Күнделік не подключён: партнёрский OAuth2 выдаётся вручную по заявке. Используется свой журнал.
- Учебники не парсятся принципиально (права издательств) — берутся только оглавления как
  метаданные, контент генерируется под цели обучения.
- Формулировки целей в демо-сиде помечены `DRAFT` и требуют сверки с приказом.

## Запуск

```bash
cp .env.example .env            # OPENAI_API_KEY, OPENAI_MODEL
cd backend && pip install -r requirements.txt
uvicorn app.main:app --port 8000
# фронт
cd web && npm i && npm run build      # статику отдаёт тот же сервис
```

`DEMO_MODE=1` включает фиксированные ответы из `seed/fixtures` — прототип переживает
отсутствие сети и лимиты API.
